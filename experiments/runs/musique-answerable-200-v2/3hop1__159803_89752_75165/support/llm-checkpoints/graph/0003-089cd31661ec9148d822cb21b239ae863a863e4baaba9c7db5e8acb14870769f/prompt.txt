Convert one source unit into a rich grounded RDF-style knowledge graph.

The source has two immutable segments: `title` and `text`.

Goals:
1. extract as many useful explicit atomic facts as possible;
2. represent them as reusable subject-predicate-object statements;
3. ground every subject, predicate, and object to exact source substrings.

Do not stop after finding only the facts needed for one downstream question.

Return ONLY:

{
  "statements": [
    {
      "subject": {
        "value": "...",
        "evidence": [
          {"segment": "title|text", "quote": "...", "occurrence": 1}
        ]
      },
      "predicate": {
        "value": "...",
        "evidence": [
          {"segment": "title|text", "quote": "...", "occurrence": 1}
        ]
      },
      "object": {
        "value": "...",
        "datatype": "... optional ...",
        "evidence": [
          {"segment": "title|text", "quote": "...", "occurrence": 1}
        ]
      }
    }
  ]
}

RULES

1. ATOMIC FACTS
Each statement expresses one relation.
Subjects and entity objects must be reusable entities/concepts, not sentences,
clauses, explanations, or lists.

Split dimensions:
"American jazz guitarist" ->
  nationality -> American
  occupation -> guitarist
  genre -> jazz

Split lists:
"CD and vinyl" -> two statements.

2. ENTITIES VS LITERALS
Subjects are always entities.
Objects without `datatype` are entities.

Use literals only for scalar values.

Allowed datatypes:
string, integer, decimal, boolean, year, yearMonth, date, dateTime

Normalize when the source provides enough precision:

"68,202,492" -> value "68202492", datatype "integer"
"6 March 2018" -> value "2018-03-06", datatype "date"
"March 2018" -> value "2018-03", datatype "yearMonth"
"2018" -> value "2018", datatype "year"

Keep imprecise scalars as strings:
"the 1950s"
"around 2018"
"35 to 40 hours per week"

Never invent missing precision.
Every `value` is a JSON string.

3. PREDICATES
Use concise lowerCamelCase relations, normally 1-4 words, e.g.:

instanceOf, nationality, occupation, genre, bornIn, bornOn,
director, writtenBy, producedBy, starring, locatedIn,
foundedBy, foundedInYear, publicationYear, headquarteredIn

Predicate evidence should be the shortest exact phrase expressing the relation.

4. LOCAL SUPPORT
A statement must be supported by one local assertion, normally one clause or
sentence.

Cross-sentence resolution is allowed only for local identity/coreference:
pronouns, aliases, abbreviations, omitted subjects, or the title.

Do not combine unrelated fragments to manufacture a relation.

5. EXACT GROUNDING
Every subject, predicate, and object requires evidence.

Each `quote` must be an exact non-empty substring of its declared segment.
Preserve capitalization, spelling, punctuation, whitespace, Unicode, etc.

Occurrences are counted independently per segment from left to right.
Use occurrence 1 unless the same quote appears multiple times.

Evidence roles must be meaningful:
- subject evidence identifies the subject;
- predicate evidence expresses the relation;
- object evidence identifies/expresses the object.

6. TITLE
Use the title when needed to resolve a local subject/object.

Example:
Title: "Maria Torres"
Text: "She founded Lumen Works."

"Maria Torres" may use title evidence "Maria Torres" plus text evidence "She".

Do not automatically make the title entity the subject of every statement.

7. SOURCE BOUNDARY
Use only explicit information in the supplied title and text.

Do not automatically add inverse, symmetric, transitive, ontology-derived,
cross-source, or external-world facts.

8. BROAD COVERAGE
Continue through the whole source.

Extract useful explicit facts about identity, type, nationality, occupation,
location, people, works, organizations, authorship, direction, production,
membership, leadership, dates, quantities, genres, formats, and other grounded
relations.

Do not manufacture facts merely to increase graph size.

Return {"statements": []} only when no useful fully grounded atomic fact exists.
